5G SBI packet capture

Capturing SBI traffic without restarting anything

HTTP/2 compresses headers in a way that makes a mid-conversation packet capture unreadable. These two tools fix that, so you can start a capture whenever you like instead of bouncing network functions first.

Why headers vanish from a capture

The problem in one page

HTTP/2 avoids repeating itself. The first time an NF sends user-agent: SMF, it spells the header out in full and both sides write it down in a numbered list. Every time afterwards, it just sends the number.

That numbered list is called the dynamic table. It is built up as the conversation goes along, and it exists only in the memory of the two programs talking. It is never sent across the network.

So if you start recording halfway through a conversation, you never saw the list being built. You get the numbers but not what they mean, and Wireshark shows you this: 

# the same request, captured mid-conversation
:method     PATCH
:path       /nnrf-nfm/v1/nf-instances/bb8a6112-...
<unknown>
<unknown>
<unknown>

This is why testing SBI normally means restarting the network functions before every capture — that forces new connections, so the capture sees the list being built from scratch. It works, but it disrupts the very system you are trying to observe.

The key idea

The list can't be recovered from a mid-conversation recording. But it can be kept in memory by something that has been watching all along. So the thing that has to start early is the decoder, not the capture.

How the fix works

Four moving parts

1. h2tapd watches, permanently

It sits on the NF host reading SBI traffic and keeps its own copy of every connection's numbered list, updating as the conversation goes. It costs about 3 MB of memory and a tenth of one CPU core, so you leave it running forever.

2. Starting a capture writes two files at once

When you ask for a capture, h2tapd starts recording packets and writes down its copy of the lists in the same moment, from the same packet stream. That pairing is the whole trick: the lists are useless unless you know exactly which byte of the conversation they correspond to.

3. h2rebuild replays the recording

Afterwards, it loads the lists, jumps to exactly the right byte, and replays your whole capture from there — following every addition and removal to the lists just as the NFs did.

4. It writes a new pcap with nothing numbered

Every header is written out in full. The result needs no lists at all, so it opens in Wireshark and reads correctly from any point in the file.

Why a snapshot at the start is enough for an hour-long capture

The lists change constantly, so people reasonably assume you'd need to keep re-saving them. You don't. The recording already contains every change; the snapshot only has to supply the starting point. Verified on a nine-minute run: 540 consecutive requests on one connection decoded correctly from a single snapshot taken at the start.

Deploying it

Once per host

  1. Build

    Static binaries with no dependencies — nothing to install on the target, not even libpcap. 

    cargo build --release --target x86_64-unknown-linux-musl

  2. Copy to the host and create the output directory

    scp target/x86_64-unknown-linux-musl/release/h2tapd \
    target/x86_64-unknown-linux-musl/release/h2rebuild \
    root@HOST:/usr/local/bin/

ssh root@HOST 'chmod +x /usr/local/bin/h2*; mkdir -p /var/lib/h2tapd'

  3. Find the interface the SBI traffic is actually on

    This catches people out. If all your NFs run on one host, they talk to each other over loopback even though their addresses look like normal network addresses. Check before you guess: 

    # does NF-to-NF traffic go over the NIC, or over lo?
ip route get 192.168.130.10 from 192.168.130.39
→ local 192.168.130.10 ... dev lo

# confirm you can actually see the traffic there
tcpdump -i lo -n -c 5 'tcp port 80'

  4. Install as a service

    A template unit means one file covers every interface you want to watch. Create /etc/systemd/system/h2tapd@.service: 

    [Unit]
Description=h2tapd HPACK table keeper on %i
After=network.target

[Service]
Type=simple
EnvironmentFile=/etc/default/h2tapd-%i
ExecStart=/usr/local/bin/h2tapd --iface %i --ports ${H2_PORTS} \
          --api ${H2_API} --out-dir ${H2_OUTDIR} --ring-bytes ${H2_RING}
Restart=always
RestartSec=2
AmbientCapabilities=CAP_NET_RAW CAP_NET_ADMIN

[Install]
WantedBy=multi-user.target

    Then a settings file per interface, /etc/default/h2tapd-lo:

    H2_PORTS=80
H2_API=127.0.0.1:9099
H2_OUTDIR=/var/lib/h2tapd/lo
H2_RING=33554432
    systemctl daemon-reload
systemctl enable --now h2tapd@lo

  5. Reset the existing connections, once

    Connections that were already open when h2tapd started are the ones it never saw from the beginning, so they still decode partially. Long-lived SBI connections may never renew on their own, so give them one nudge. Restarting the SBI NFs is cleanest; killing the sockets is quicker: 

    # quicker: NFs reconnect within seconds
ss -K state established dst 192.168.130.0/24 dport = :80

# cleaner: restart the SBI network functions
systemctl restart open5gs-nrfd open5gs-scpd open5gs-amfd ...

    This is a one-time step, not something you repeat before every capture. That is the entire point of the tool.

  6. Confirm it's ready

    You want exact to equal dirs. That means every connection is fully understood and any capture you take will decode completely. 

    curl -s localhost:9099/health

conns=15  dirs=30  exact=30  poisoned=0  gaps=0

Taking a capture

Every time

# 1. start — writes the pcap and the snapshot together
curl -XPOST localhost:9099/captures -d '{"name":"nrf-reg-test"}'

{
  "capture_id":      "nrf-reg-test",
  "pcap":            "/var/lib/h2tapd/lo/nrf-reg-test.pcap",
  "snapshot":        "/var/lib/h2tapd/lo/nrf-reg-test.snapshot.json",
  "conns_total":     15,
  "conns_usable":    15,
  "conns_degraded":  0
}

# 2. run your test traffic …

# 3. stop
curl -XDELETE localhost:9099/captures/nrf-reg-test
Check this before you run the test, not after

conns_degraded tells you up front which connections can't be vouched for, and each one comes with a reason. Finding out now costs you nothing; finding out after an hour of analysis costs you the hour.

Connections that start during your capture need no snapshot at all — they're recorded from their first packet, so they're understood from first principles.

Reading the result

Turning the recording into something you can open

h2rebuild -r nrf-reg-test.pcap \
          -s nrf-reg-test.snapshot.json \
          -w nrf-reg-test-readable.pcap \
          --jsonl decoded.jsonl

packets in/out    1932 -> 1061
connections       16 (32 seeded from snapshot)
header blocks     381 (381 fully decoded, 0 partial)

Open nrf-reg-test-readable.pcap in Wireshark. Every header is spelled out, so it reads correctly no matter where you jump to in the file.

--jsonl additionally writes one JSON line per request or response, if you'd rather grep or diff than click. It roughly triples the run time, so leave it off when you only want the pcap.

What "missing" looks like

The tool never invents a header. If something genuinely can't be recovered, it says so in place, and you can search for it:

What you seeWhat it means
@unresolved-idx-63 A number whose meaning was set before the tool started watching. An honest gap.
@hpack-decode-failed A header block that couldn't be read at all — shown rather than silently dropped.
pre-snapshot skip A few hundred bytes recorded just before the capture point. Traffic from before you pressed start, not part of your test.
MISALIGNED The recording and the lists don't line up, so the lists were not applied. Never a wrong answer.

Checking health

Two commands worth knowing

GET /health is the one to glance at before and after a long capture. The number that matters is reassembly_gaps: it counts moments where h2tapd missed a packet, which is the only thing that degrades a long recording.

FieldHealthyMeaning
exact vs dirsequalEvery connection fully understood
reassembly_gaps0No packets missed
dirs_poisoned0No connection has lost its place
conns_degraded0Every connection safe to rebuild

GET /connections gives the same picture per connection, with the reason attached whenever something isn't right.

Things that will bite you

Learned the hard way, so you don't have to

Restarting h2tapd wipes everything it knows

All the numbered lists live in memory. If you restart or upgrade the daemon, live connections drop back to partial decoding until they renew — so reset the connections again afterwards, exactly as you did on first install.

Watch on the same segment as the traffic

If there's a SEPP, a proxy or a service mesh between the two NFs, that's a different conversation with a different set of lists. h2tapd has to be watching the same hop your capture covers.

The rebuilt pcap is for reading, not for TCP forensics

Headers, payloads, stream IDs, ordering and timestamps are all faithful. The TCP layer underneath is regenerated, so packet boundaries, sequence numbers and retransmissions are not the originals. Keep the original file for anything at that level.

Plaintext only

If SBI runs over TLS, the compression happens inside the encryption and none of this applies without keys.

Keep the ring buffer short

--ring-secs (default 5) matters more than --ring-bytes. It only exists to complete a half-received message. Set it to hours and your captures fill with long-dead connections the snapshot knows nothing about — the capture then looks broken when it isn't.
